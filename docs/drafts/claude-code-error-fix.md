# 클로드 코드로 에러 해결하는 3단계

> 💡 **한 줄 요약:** 클로드 코드로 에러 해결은
> 에러를 그대로 보여 주기, 원인부터 찾고 고치기,
> 증거로 확인하기의 3단계면 충분합니다.

[IMAGE: 썸네일 | 설명: 클로드 코드로 에러 해결하는 3단계 대표 이미지]

"에러가 떴는데 클로드에게 어떻게 물어야
제대로 고쳐 줄지 모르겠어요" 하시는 분들을 위해 준비했습니다.
결론부터 말씀드리면, **클로드 코드로 에러 해결**은
에러 메시지와 재현 방법을 그대로 넘기고,
고칠 방법을 먼저 들어 본 뒤 고르게 하고,
테스트 결과 같은 증거로 확인하면 끝납니다.

저도 처음엔 에러의 마지막 줄만 잘라 붙이고
"이거 왜 안 돼?"라고만 물었다가 엉뚱한 답을 받곤 했어요.
에러를 줄여서 넘기면 클로드도 원인을 짐작으로 찾게 된다는
이야기가 여러 곳에서 반복해서 나오더라고요.

오늘 이 글 하나만 끝까지 읽으시면 에러가 나도 당황하지 않고
순서대로 클로드에게 맡기실 수 있습니다.
예시 문장과 기능 설명은 [Claude Code 공식 문서](https://code.claude.com/docs/en/common-workflows)를
2026년 10월 29일에 확인해 정리했습니다.

---

## 🛠️ 시작하기 전에 준비할 것들

* **준비물:** 클로드 코드 설치, 에러가 나는 프로젝트 폴더
* **있으면 좋은 것:** 에러를 다시 내 볼 수 있는 명령
* **난이도:** 초급, 에러 메시지를 복사할 줄 알면 충분합니다

에러가 난 프로젝트의 맨 위 폴더에서 클로드 코드를 실행해 주세요.
그래야 에러가 가리키는 파일을 클로드가 직접 열어 보며
원인을 찾을 수 있습니다.
세 단계의 흐름을 한 장으로 먼저 보고 넘어가겠습니다.

[IMAGE: 다이어그램 | 설명: 클로드 코드로 에러 해결하는 보여 주기, 원인 찾고 고치기, 증거로 확인 3단계 흐름]

## Step 1. 에러는 클로드 코드에 어떻게 보여 줄까?

처음 할 때 가장 많이 실수하는 부분은
에러를 내 마음대로 줄여서 전달하는 것입니다.
전체 에러에는 어느 파일 몇 번째 줄에서 문제가 생겼는지
차례로 적혀 있어서, 통째로 붙이는 편이 원인 찾기에 유리합니다.

공식 문서가 권하는 전달 내용은 아래 네 가지입니다.
아래 순서대로 차근차근 따라와 주세요.

1. 에러 메시지 전체를 붙입니다. (스택 트레이스까지 그대로)
2. 에러를 다시 내는 명령을 알려 줍니다.
3. 에러가 나기까지 어떤 순서로 했는지 적습니다.
4. 매번 나는지, 가끔만 나는지 알려 줍니다.

스택 트레이스는 에러가 나기까지 거쳐 온 함수와 파일의 목록인데요,
맨 위 한 줄만 보면 놓치는 원인이 아래쪽에 숨어 있는 경우가 많습니다.
네 가지를 한 번에 담으면 아래처럼 됩니다.

```
npm test를 실행하면 에러가 나. 아래가 전체 에러야.
(에러 전체 붙여 넣기)
매번 같은 테스트에서 실패하고, 로그인 코드를 고친 뒤부터 그래.
```

화면에 뜬 에러라면 캡처해서 그대로 보여 줘도 됩니다.
이미지를 복사한 뒤 `Ctrl+V`(Windows와 WSL은 `Alt+V`)로 붙이고
"이 에러의 원인이 뭐야?"라고 물으면 됩니다.
로그 파일이 길다면 터미널에서 바로 넘기는 방법도 있습니다.

```bash
cat error.log | claude -p "무슨 문제인지 알려줘"
```

> 📌 **전문가 Tip:** "고쳐졌다"의 기준도 처음에 함께 적어 주세요.
> 공식 문서는 파일, 증상, 고쳐진 모습을 먼저 알려 주면
> 수정 요청을 한 번 덜 하게 된다고 안내합니다.

## Step 2. 클로드 코드로 원인을 찾고 고치려면?

에러를 넘겼다면 이제 원인을 찾아 고칠 차례입니다.
바로 "고쳐줘"라고 하기보다 고칠 방법을 몇 가지 먼저 들어 보는 것이
공식 문서가 안내하는 순서인데요.
방법을 비교해 보고 내가 고르면 엉뚱한 곳을 고칠 일이 줄어듭니다.

1. 원인을 먼저 설명해 달라고 합니다.
2. 고칠 방법을 몇 가지 제안받습니다.
3. 그중 하나를 골라 적용하게 합니다.

```
이 에러의 원인을 먼저 설명하고, 고칠 방법을 몇 가지 제안해줘
두 번째 방법으로 user.ts를 고쳐줘
```

(이때 주의할 점은 고치기 전에 계획을 꼭 보고 싶다면
Plan 모드를 켜 두는 것입니다.
`Shift+Tab`을 눌러 `⏸ plan mode on`이 보이면
내가 승인하기 전까지 파일을 고치지 않습니다.)

에러를 재현하는 테스트가 없다면 그것부터 쓰게 하는 방법도 좋습니다.
공식 문서의 예시도 실패하는 테스트를 먼저 쓰고
그다음에 고치라고 요청하는데요,
이렇게 하면 다 고친 뒤 그 테스트로 바로 확인할 수 있죠.

[IMAGE: 포인트카드 | 설명: 클로드 코드 Step 2 원인 설명, 방법 제안, 골라서 적용하는 에러 수정 순서]

> 📌 **전문가 Tip:** 남이 짠 코드의 버그나 가끔만 실패하는 테스트처럼
> 놓치기 쉬운 에러라면 `/effort high`를 입력해 보세요.
> 경우의 수를 더 따져 보고 확인도 더 하고 답합니다.

### 같은 수정만 반복할 때는 어떻게 할까?

고쳤다는 말을 듣고 다시 돌려 보면 같은 에러가 나고,
다시 부탁하면 비슷한 수정을 또 내놓는 경우가 꽤 많더라고요.
저도 이럴 때 같은 부탁을 계속 반복하다가 대화만 길어진 적이 있어요.

공식 문서는 두 번 고쳐도 안 되면 세 번째로 부탁하지 말고
`/clear`로 대화를 비운 뒤 새로 요청하라고 권합니다.
실패한 시도가 쌓인 대화를 클로드가 계속 다시 읽기 때문이죠.
상황에 맞는 방법을 표로 정리했습니다.

| 방법 | 하는 일 | 이럴 때 써요 👍 |
| :--- | :--- | :--- |
| **Esc** | 진행 중인 작업을 멈추고, 그때까지 한 일은 남김 | 엉뚱한 방향으로 갈 때 |
| **/rewind** | 코드나 대화를 이전 요청 시점으로 되돌림 | 수정이 오히려 망가뜨렸을 때 |
| **/clear** | 대화를 비우고 새로 시작 | 두 번 고쳐도 그대로일 때 |

[IMAGE: 비교표 | 설명: 클로드 코드로 에러 해결이 막혔을 때 쓰는 Esc, /rewind, /clear 비교]

`/clear` 뒤의 새 요청에는 지금까지 알아낸 것을 담아 주세요.
어떤 방법을 써 봤고 왜 안 됐는지까지 적으면
같은 수정으로 돌아갈 일이 줄어듭니다.

## Step 3. 에러가 정말 고쳐졌는지 어떻게 확인할까?

하지만 중요한 건 "고쳤습니다"라는 말이 아니라
**다시 돌려 봤을 때 에러가 사라졌는지**이겠죠.
코드 대신 테스트를 바꿔서 통과시키거나,
실패하는 테스트를 건너뛰게 해 두고 끝났다고 한 사례가 여러 번 보고됐습니다.

저도 통과했다는 말만 믿고 넘어갔다가
나중에 테스트의 기대값이 바뀌어 있는 걸 보고 다시 고친 적이 있어요.
그래서 지금은 확인 방법을 처음부터 정해 두고 부탁합니다.

1. 고친 뒤 실행할 테스트 명령을 정해 줍니다.
2. 테스트 파일은 고치지 말라고 적어 둡니다.
3. 실행한 명령과 출력을 그대로 보여 달라고 합니다.

```
테스트 파일은 고치지 말고 코드만 고쳐줘.
고친 뒤 npm test를 실행하고, 통과할 때까지 계속해줘.
마지막에 실행한 명령과 결과를 그대로 보여줘.
```

공식 문서도 "테스트 다 통과했어요"라는 말만으로는
알 수 있는 게 거의 없다며, 실행한 명령과 출력을 증거로 받으라고 안내합니다.
출력을 직접 읽는 편이 내가 테스트를 다시 돌리는 것보다 빠르기도 하고요.

### 다음에 같은 에러를 줄이려면?

테스트, 타입 검사, 린트를 돌리는 정확한 명령은 `CLAUDE.md`에 적어 두세요.
린트는 코드의 실수와 형식을 자동으로 검사하는 도구를 말합니다.
공식 문서도 이 저장소에서 작업을 확인하는 방법을
`CLAUDE.md`에 남기라고 권하는데요,
그러면 매번 확인 명령을 설명하지 않아도 됩니다.
